## 1. Назначение и ожидаемый результат

Разработать библиотеку, которая на каждом шаге генерации LLM определяет множество допустимых следующих токенов согласно заданным ограничениям. Библиотека хранит состояние разбора между шагами и обновляет его после принятия токена.

Для поддерживаемых ограничений завершённый ответ должен соответствовать заданной структуре. Основные применения: JSON для программной обработки, аргументы вызова инструментов, извлечение структурированных данных и выбор из фиксированного набора значений.

Пример: для схемы с полем action из набора buy/sell и целочисленным amount движок запрещает продолжения, которые не могут завершиться допустимым документом. Выбор содержательно правильного действия и числа остаётся задачей модели.

Результат работы — самостоятельная реализация идей эффективного constrained decoding на Zig. XGrammar и llguidance используются как архитектурные ориентиры и обязательные участники сравнения. Одновременный запуск двух библиотек с пересечением их масок не является целевой архитектурой.

### 1.1. Гипотеза ценности

Проверить возможность совместить:

- небольшой объём подготовки для новых схем;
- переиспользование вычислений для повторяющихся схем и состояний;
- управляемое потребление памяти;
- предсказуемую задержку построения маски;
- удобное встраивание через C ABI и Python.

Замена языка сама по себе не считается преимуществом. Ускорение всей генерации, уменьшение памяти и преимущество над существующими движками должны подтверждаться измерениями.

### 1.2. Контекст существующих решений

XGrammar использует предварительное вычисление масок; в XGrammar-2 также описаны межграмматический кэш, сжатие повторяющихся состояний и пакетные API. Сравнение должно учитывать эти возможности, а не только раннюю реализацию XGrammar. [Описание XGrammar-2](https://blog.mlc.ai/2026/05/04/xgrammar-2-fast-customizable-structured-generation).

llguidance использует разделение лексера и парсера, алгоритм Earley, дерево байтовых представлений токенов и оптимизацию групп токенов — slicer. Это ориентиры для исследования алгоритмов, а не требование дословно воспроизвести внутреннюю архитектуру. [Техническое описание llguidance](https://guidance-ai.github.io/llguidance/llg-go-brrr).

Опубликованные авторами показатели производительности не принимаются как результаты нового проекта и не используются для обещаний ускорения.

## 2. Границы ответственности

### 2.1. Внутри библиотеки

- проверка и компиляция поддерживаемых ограничений;
- представление токенизатора, необходимое для проверки допустимости токенов;
- инкрементальный разбор с состоянием на каждую последовательность;
- построение маски допустимых токенов;
- ограниченный по памяти кэш;
- пакетный интерфейс;
- диагностика, лимиты ресурсов, C ABI и Python-обвязка.

### 2.2. Вне ядра

- forward-проход модели, веса, attention и KV-cache;
- temperature, top-k, top-p, RNG и собственно sampling;
- обучение и дообучение моделей;
- проверка истинности и полезности ответа;
- произвольный Python-код ограничений;
- исправление ранее сформированного неправильного ответа;
- самостоятельный inference-сервер.

### 2.3. Граница CPU/GPU

Ядро получает ограничения, токены и состояние; возвращает маску. Матрица логитов не передаётся с GPU на CPU ради работы движка.

Для GPU-модели маска переносится на устройство логитов и применяется адаптером. В MVP допустимы обычные операции PyTorch; собственные CUDA/Triton-ядра не обязательны. Распаковка маски, перенос данных, синхронизации и применение к логитам входят в интеграционные измерения.

Для CPU-модели маска применяется на CPU. Наличие CPU-маски не означает автоматически zero-copy для GPU.

## 3. Термины и контракт корректности

| Термин | Значение |
|---|---|
| Ограничение | Схема или грамматика, задающая допустимый язык ответов |
| Профиль генерации | Дополнительные явные правила сериализации: порядок ключей, пробелы, представление чисел |
| Состояние | Данные, достаточные для продолжения разбора без повторного чтения всей истории |
| Маска | Битовое множество разрешённых token IDs; единица означает разрешение |
| Холодный запуск | Первый запрос к схеме без её подготовленных данных в кэше |
| Тёплый запуск | Повторное использование подготовленной схемы в том же процессе |
| Эталонный интерпретатор | Независимая медленная реализация семантики для проверки ядра |
| Завершённый ответ | Документ, принятый грамматикой, после которого принят разрешённый EOS |

### 3.1. Допустимость следующего токена

Токен разрешён, если после его принятия существует конечное продолжение из поддерживаемых токенов, заканчивающееся допустимым завершённым ответом. Одного отсутствия немедленной синтаксической ошибки недостаточно: тупиковые префиксы должны исключаться.

Проверяется весь байтовый фрагмент токена. Токен может включать несколько знаков пунктуации, пересекать границу поля или содержать часть многобайтового UTF-8 символа.

Для поддержки такого контракта MVP принимает только токенизаторы с проверенной моделью декодирования и достаточным покрытием байтов/символов для целевого языка. Неподдерживаемый токенизатор отклоняется до генерации. Допустимость не учитывает оставшийся пользовательский лимит max_new_tokens: достижение этого лимита может прервать корректный префикс.

### 3.2. Два обязательных свойства

1. Безопасность ограничений: движок не разрешает продолжение, нарушающее принятый язык генерации.
2. Полнота относительно этого языка: движок не запрещает допустимое продолжение из-за эвристики или кэширования.

Если профиль генерации сужает множество представлений, это отражается в метаданных компиляции. Полнота относительно всех возможных сериализаций исходной JSON Schema не заявляется.

### 3.3. Завершение и прерывание

- EOS разрешается только в принимающем состоянии.
- При нескольких EOS применяются одинаковые правила для всех зарегистрированных EOS IDs.
- Истечение времени, отмена, лимит токенов или ресурсов возвращают признак незавершённого ответа и причину.
- Корректный префикс не выдаётся за готовый JSON.
- Отказ модели текстом допустим только если он явно включён в язык ограничений.
- Грамматическая корректность не означает достоверность данных или безопасность вызова инструмента.

## 5. Поддерживаемые ограничения

### FR-1. Профиль JSON Schema

Вход: UTF-8 JSON, профиль Draft 2020-12. Для MVP применяется следующий закрытый список. Неизвестные проверочные ключевые слова вызывают UnsupportedFeature с JSON Pointer к месту ошибки.

| Элемент | Поддержка MVP |
|---|---|
| type | Одна строка: object, array, string, integer, number, boolean, null |
| properties, required | Да; обязательный явный список required, неизвестные имена в нём отклоняются |
| additionalProperties | Для object обязательно явно false |
| items | Одна поддерживаемая схема для всех элементов массива |
| minItems, maxItems | Да, неотрицательные целые; противоречие min > max — ошибка |
| minLength, maxLength | Да, длина декодированного значения в Unicode scalar values |
| enum, const | Скалярные значения; ограничения проверяются совместно с type и длиной |
| $defs, $ref | Локальные ссылки внутри документа; только ациклический граф |
| $schema | Допускается идентификатор Draft 2020-12; другой диалект — ошибка |
| title, description, $comment, examples, default | Аннотации; не влияют на маску, default не вставляет значение |
| anyOf, oneOf, allOf, not, if/then/else | Вне MVP |
| minimum, maximum, multipleOf и exclusive-варианты | Вне MVP; не игнорируются |
| pattern, format, patternProperties | Вне MVP |
| uniqueItems, contains, dependentSchemas, unevaluatedProperties | Вне MVP |
| Внешние ссылки и загрузка схем по сети | Не поддерживаются |

Для каждого объектного узла обязательны properties и additionalProperties: false. Пустые properties и required: [] допустимы. Необязательные поля можно пропускать; повторять ключ нельзя. Для массивов items обязателен. Ограничения на enum/const применяются к JSON-значениям, включая корректное сравнение чисел без округления через binary64.

В MVP каждое значение схемы должно быть объектом с поддерживаемым type либо чистой локальной ссылкой $ref. Boolean schemas и проверочные ключевые слова рядом с $ref отклоняются. Аннотации рядом со ссылкой допускаются. Отсутствие ограничителя длины означает отсутствие семантического верхнего предела; лимит ресурсов движка остаётся отдельным механизмом.

### FR-2. Профиль сериализации JSON

Для ограничения сложности MVP используется именованный профиль canonical-v1:

- ключи объектов следуют порядку их объявления в properties; порядок сохраняется при чтении схемы;
- необязательные ключи сохраняют относительный порядок при пропуске других ключей;
- пробелы вне строк отсутствуют;
- ключи и строковые литералы кодируются единым документированным JSON-экранированием;
- строковые значения представляются UTF-8; кавычка, обратный слеш и управляющие символы экранируются;
- для управляющих символов задаётся одна таблица экранирования: короткие escapes там, где они существуют, иначе нижнерегистровый u00xx;
- произвольные альтернативные Unicode escapes вне указанной таблицы не принимаются в этом профиле;
- незавершённый UTF-8 допустим только как промежуточное состояние между токенами; завершённые значения должны содержать валидные Unicode scalar values;
- integer сериализуется десятичной записью без дробной части и экспоненты; number — по синтаксису JSON-числа;
- NaN и бесконечности не являются JSON-числами и запрещены.

Это явное ограничение представления. Например, экспоненциальная запись целого значения может быть допустима исходной JSON Schema, но не языком integer в canonical-v1. Такие различия отражаются в отчёте компилятора и тестах.

Для enum/const числовых значений компилятор выбирает документированную точную десятичную сериализацию; равные JSON-значения нормализуются без потери точности. Исходная схема с повторяющимися ключами отклоняется.

Конкретный список допустимых escapes и нормализация числовых литералов оформляются в semantics.md до реализации оптимизированного ядра.

### FR-3. Буквальные альтернативы

Поддержать отдельный формат: непустой список строк UTF-8, из которых выбирается ровно одна. Поддержать общий префикс, пустую строку как один из вариантов, Unicode и токены, перекрывающие несколько символов. Не смешивать этот формат с произвольной regex.

### FR-4. Диагностика и невозможные ограничения

Компилятор возвращает профиль, поддержанные возможности и диагностику. Для известных противоречий возвращается UnsatisfiableConstraint. Структурные ограничения ресурсов не должны молча изменять схему.

Если во время генерации нет разрешённых токенов, возвращается DeadEnd с состоянием и причиной для отладки. Запрещено автоматически разрешать весь словарь или EOS.

### FR-5. Компилятор и внутренняя грамматика

- Схема преобразуется в неизменяемое внутреннее представление.
- Повторения массивов и строк представлены счётчиками/узлами повторения; нельзя разворачивать большой maxItems в пропорциональное число копий грамматики.
- Разделить обработку лексических элементов и структуры там, где это уменьшает стоимость проверки.
- Выбор конкретного парсера оформляется ADR с измерением времени, памяти и сложности поддержки; Earley — исследуемый вариант, не обязательное условие.
- Подготовленные данные одной схемы разделяются между сессиями без копирования всей грамматики.
- Ошибки разбора схемы и несовместимость профиля выявляются до первого forward-прохода.

### FR-6. Представление токенизатора

- Передавать таблицу токенов и специальные IDs один раз на контекст токенизатора.
- Для поддерживаемых токенизаторов использовать точное байтовое представление; одиночный decode(token_id) не считать универсальным способом получения байтов.
- Учитывать byte fallback, добавленные токены, частичные UTF-8 последовательности и специальные токены.
- BOS/PAD и другие служебные токены запрещены внутри активного документа, если для них нет явно описанной роли.
- Обычные токены с пустым представлением отклоняются при подготовке токенизатора; EOS обрабатывается отдельно.
- Строить компактное дерево токенов с отсечением недопустимых поддеревьев.
- Ключ идентичности токенизатора включает словарь, отображение байтов, decoder-настройки и специальные IDs.
- Нельзя подменять токенизатор у уже созданной сессии.
- В MVP подтвердить две семьи: byte-level BPE и токенизатор с byte fallback. Конкретные публичные tokenizer artifacts и revisions фиксируются на этапе 0.
- Если декодирование зависит от контекста и не выражено выбранным адаптером, вернуть UnsupportedTokenizer, а не применять приближение.

### FR-7. Состояние сессии

Сессия хранит состояние парсера, незавершённый лексический элемент/UTF-8, счётчики ограничений и статистику. Вся история ответа не пересылается и не разбирается заново на каждом шаге.

Обязательные операции:

1. Создать сессию с пустым префиксом ответа.
2. Построить маску без изменения логического состояния.
3. Принять выбранный token ID.
4. Проверить возможность завершения.
5. Финализировать, отменить или уничтожить сессию.

Состояния жизненного цикла: active, finished, aborted. После finished/aborted принимать токены нельзя. Повторный запрос маски в одном active-состоянии возвращает одинаковый результат. Принятие запрещённого токена возвращает InvalidToken без изменения логического состояния.

Prompt не является частью генерируемого JSON. Продолжение заранее заполненного JSON-префикса вне MVP; его нельзя неявно получать из конца prompt.

Для ограниченного профиля 1.0 персистентное состояние должно хранить достаточные счётчики и контекст, не накапливая полный текст неограниченной строки. Объём состояния и рабочих буферов отдельно учитывается в лимитах.

### FR-8. Маска

- Основной формат — массив uint32, размер ceil(vocab_size / 32).
- Для token ID t используется слово t / 32 и бит t % 32; единица означает разрешение.
- Неиспользуемые биты последнего слова равны нулю.
- Специальный EOS разрешается по правилу из раздела 3.
- Входной/выходной буфер принадлежит вызывающей стороне, переиспользуется между шагами.
- Сначала обеспечить точный алгоритм без кэша; все оптимизации должны давать побитово ту же маску.
- Не вводить приблизительные фильтры, способные разрешить запрещённый токен или потерять разрешённый.

### FR-9. Режимы вычисления и адаптивность

Обязательные режимы:

- lazy: вычисление по текущему состоянию с минимальной предварительной подготовкой;
- adaptive: тот же точный алгоритм с ограниченным кэшированием подготовленных фрагментов/масок по фактическому повторному использованию;
- precompute: экспериментальная подготовка выбранных подструктур в пределах заданного бюджета; полное перечисление всех состояний не требуется.

В MVP адаптивность означает выбор того, что сохранять и переиспользовать в кэше. Полная смена парсера в середине сессии и обучение отдельной модели выбора стратегии не требуются.

Политика использует число обращений, измеренную стоимость построения, размер записи и доступную память. Пороги конфигурируются и фиксируются в отчёте. Стоимость ведения статистики включается в измерения.

Для каждого режима должен существовать явный выбор пользователем. Отключение кэша меняет производительность, но не язык и не маски.

### FR-10. Кэш и бюджет памяти

- Разделить память токенизатора, компилятора, грамматик, сессий, временных буферов и кэша.
- Все выделения ядра проходят через учитывающий allocator; резервируемая память также учитывается.
- Кэш имеет жёсткий бюджет и политику вытеснения; при заполнении работа продолжается через lazy, если остальные лимиты позволяют.
- Общий лимит ядра включает временные данные компиляции и все живые объекты контекста, а не только полезную нагрузку кэша.
- Достижение общего лимита возвращает ResourceLimit; схема не упрощается, маска не ослабляется.
- Межграмматическое переиспользование разрешается только для доказанно эквивалентных подструктур.
- Ключ кэша учитывает профиль, семантику грамматики, токенизатор, версию формата и контекст, влияющий на допустимость. Один последний token ID не является достаточным ключом состояния.
- Коллизия хэша проверяется сравнением идентичности/содержимого, а не считается совпадением.
- Вытеснение не инвалидирует данные, которыми пользуется активная сессия.
- Кэш на диске и совместное использование между процессами вне MVP.

Начальные значения по умолчанию, пересматриваемые по результатам этапа 0: общий бюджет ядра 256 MiB; кэш до 64 MiB; состояние и рабочие данные одной сессии до 8 MiB; входная схема до 1 MiB; структурная глубина до 64. Все ограничения публичны и настраиваются; их несовместимая комбинация выявляется при создании контекста. При нехватке бюджета для токенизатора контекст не создаётся.

### FR-11. Батч и потоки

- Обрабатывать массив независимых сессий одним C ABI вызовом.
- Поддержать разные схемы внутри батча.
- Завершённые элементы не обрабатываются ядром повторно; сопоставление строк и сессий сохраняет адаптер.
- Маски выдаются в порядке переданных сессий с отдельным статусом каждой строки. Ошибка одной строки не должна скрывать статус остальных.
- Последовательное исполнение обязательно; внутренний пул потоков — оптимизация после профилирования.
- Независимые сессии допускают параллельные вызовы. Одновременное изменение одной сессии запрещено контрактом и блокируется Python-обвязкой.
- Результат не зависит от числа рабочих потоков.
- Нельзя создавать новые потоки на каждом токене; число потоков явно ограничивается, чтобы не конкурировать бесконтрольно с PyTorch.

## 7. C ABI и Python

### FR-12. C ABI

Поставить версионированный заголовок с opaque handles контекста, грамматики и сессии. Структуры параметров содержат размер и версию; числовые поля используют типы фиксированной ширины, размеры буферов — size_t.

Минимальный набор экспортируемых операций:

~~~text
zg_abi_version
zg_context_create / zg_context_destroy
zg_compile / zg_grammar_release
zg_session_create / zg_session_destroy
zg_fill_mask / zg_fill_masks_batch
zg_accept_token
zg_can_end / zg_finish / zg_abort
zg_get_stats
~~~

Окончательные сигнатуры, кодировки сообщений и таблица кодов ошибок оформляются в include/zig_constraints.h до начала Python-интеграции.

Контракт владения:

- схема и конфигурация копируются/компилируются при создании; указатель на временный Python-буфер не сохраняется;
- данные токенизатора принадлежат контексту после подготовки;
- контекст должен жить дольше его грамматик и сессий; попытка штатного уничтожения занятого контекста возвращает Busy;
- выходная маска записывается в предоставленный буфер достаточного размера и выравнивания;
- заполнение маски не сохраняет указатель на неё после возврата;
- при ошибке маска считается недействительной и не применяется;
- штатные ошибки передаются кодом и диагностикой; не пересекают ABI как Zig error union или panic;
- строки диагностики имеют явно заданное владение и срок жизни; глобальный изменяемый last_error не используется.

Ядро валидирует размеры, переполнения и параметры. Для C-клиента сохраняется обязанность передавать живые корректные указатели: произвольный dangling pointer невозможно сделать безопасным проверкой длины. Гарантия отсутствия падений относится к корректному использованию ABI и обрабатываемым ошибкам данных.

### FR-13. Python-пакет

Предпочтительная схема MVP: ядро Zig с C ABI и небольшое CPython-расширение на C, которое отвечает за объекты Python и GIL. C-код не дублирует алгоритмы построения масок. При выборе другого моста оформить ADR с измерением стоимости вызова и упаковки.

- Использовать Limited API с целевым abi3 для Python 3.10+, если все необходимые функции доступны; это проверяется сборкой и тестами на этапе 0.
- Если обнаружено ограничение Limited API, явно перейти на wheels для конкретных версий Python и обновить матрицу релиза. Нельзя помечать обычную сборку как abi3.
- Во время нативного вычисления освобождать GIL; объекты и буферы удерживать до завершения вызова.
- Рабочие буферы закрыты от конкурентной записи со стороны Python; одна сессия сериализует свои операции.
- Ошибки ABI преобразуются в типизированные Python-исключения.
- Ядро импортируется без torch. Интеграция с Transformers подключается отдельным extra.
- Контекстные менеджеры обеспечивают явное освобождение ресурсов; финализатор — дополнительная защита.

Пример целевого пользовательского API, уточняемый без изменения семантики:

~~~python
from zig_constraints import Engine
from zig_constraints.transformers import constrained_generate

schema = {
    "type": "object",
    "properties": {
        "action": {"type": "string", "enum": ["buy", "sell"]},
        "amount": {"type": "integer"},
    },
    "required": ["action", "amount"],
    "additionalProperties": False,
}

with Engine(mode="adaptive", memory_limit_mb=256) as engine:
    constraint = engine.compile(schema, tokenizer, profile="canonical-v1")
    result = constrained_generate(
        model,
        tokenizer=tokenizer,
        constraint=constraint,
        inputs=inputs,
        max_new_tokens=128,
    )
    # result содержит sequences, completed по каждой строке и stop_reason.
~~~

## 8. Интеграция с Transformers

### FR-14. Поддерживаемый путь

- Decoder-only текстовые модели, один процесс, одно устройство модели: CPU или одна CUDA GPU.
- Greedy и sampling, num_beams=1, num_return_sequences=1; фиксированный батч.
- Разные длины prompt с документированным left padding.
- Один заранее выбранный диапазон версий Transformers/PyTorch, зафиксированный на этапе 0; обещание совместимости со всеми версиями запрещено.
- Предпочитать публичные logits processor/stopping criteria. Если для корректной финализации нужен wrapper вокруг generate, использовать локальный wrapper, не глобальный monkey-patch.
- Состояние синхронизируется только с реально выбранными токенами. Последний токен и EOS должны учитываться даже если generate больше не вызовет processor.
- Для результата из-за лимита длины/времени вернуть completed=false по незавершённым строкам.
- Неподдерживаемый режим выявляется до генерации.

Адаптер не обещает удалять завершённые строки из forward-батча или экономить их KV-cache: это ответственность inference engine.

### FR-15. Порядок маскирования и конфликты

- Ограничения должны применяться до top-k/top-p, чтобы выбор кандидатов учитывал допустимый язык.
- Последующие операции не должны повторно разрешать запрещённый token ID.
- На этапе интеграции зафиксировать фактический порядок processor/warper в поддерживаемой версии HF и покрыть его тестами.
- Допускается финальная повторная защитная маска, если она нужна для выполнения контракта; её стоимость учитывается.
- Forced EOS при max_length, пользовательские processors и другие конфликтующие настройки не принимаются без отдельной доказанной схемы совместимости.
- Если пересечение ограничений с прочими настройками оставило только минус бесконечности либо появились некорректные вероятности, вернуть явную ошибку; не сэмплировать случайный токен.
- При отсутствии пакета или неподдерживаемой схеме нельзя незаметно продолжать без ограничений.

### FR-16. Fallback

MVP по умолчанию возвращает явную ошибку UnsupportedFeature/UnsupportedMode. Fallback на XGrammar или llguidance может быть добавлен только как отдельная явно включённая возможность с проверенным совпадением профиля.

Fallback означает запуск другого движка с сохранением контракта ограничений, а не отключение проверки. Переключение после начала ответа требует переноса/восстановления состояния и вне MVP.

### FR-17. Перекрытие CPU/GPU

Базовый синхронный путь обязателен. Вычисление следующей маски параллельно с forward рассматривается после его корректной реализации.

При оптимизации явно учитывать зависимость от предыдущего выбранного токена, передачу token IDs на CPU, перенос маски обратно, время запуска GPU-операций и синхронизацию. Не считать параллелизм достигнутым только из-за использования отдельного потока.

## 9. Нефункциональные требования

### NFR-1. Корректность и детерминизм

- При одинаковых токенизаторе, профиле, схеме и префиксе все режимы дают одинаковую маску.
- Вытеснение кэша, изменение числа потоков и повторное создание сессии не меняют допустимый язык.
- RNG не входит в ядро. Совпадение seed между разными sampling-реализациями не является его обязательством.
- Метрики покрытия схем отделяются от показателей скорости: неподдержанные схемы не исчезают из отчёта.

### NFR-2. Работа с памятью и ошибками

- Выделения памяти явные и учитываемые; возврат памяти проверяется после уничтожения сессии/контекста.
- Отсутствие роста RSS не требуется во время легитимного заполнения кэша. Проверяются плато при фиксированной нагрузке и отсутствие накопления после циклов create/destroy.
- После прогрева маски одного состояния не должны каждый раз создавать новые крупные буферы. Абсолютное отсутствие аллокаций для любых новых грамматик/состояний не требуется.
- Ошибки входа, превышение лимита и отмена обрабатываются штатно; частично принятый токен недопустим.
- Если внутренняя ошибка не позволяет гарантировать сохранность состояния, сессия помечается aborted и не используется повторно.
- Компиляция и построение маски принимают лимит работы и сигнал отмены. Проверки выполняются между ограниченными порциями работы; максимальный интервал реакции измеряется и фиксируется на этапе 0. Превышение бюджета возвращает ResourceLimit/Cancelled, не частичную маску. Это защита от чрезмерной стоимости, а не обещание жёсткого real-time дедлайна.

### NFR-3. Zig, сборка и платформы

- На этапе 0 зафиксировать точную стабильную версию Zig и контрольную сумму toolchain в manifest; плавающий master не используется в релизной сборке.
- Debug/ReleaseSafe применяются в проверках. ReleaseSafe — исходный режим распространения.
- ReleaseFast допускается только после сравнения и повторного прохождения проверок; отключение runtime checks не является обработкой ошибок. [Режимы Zig](https://ziglang.org/documentation/master/#Build-Mode).
- Скалярный путь обязателен. SIMD и CPU dispatch добавляются по результатам профилирования; wheel не должен требовать AVX-512 или инструкции машины сборки без проверки на целевой CPU.
- C ABI не зависит от Zig runtime-типов. Необязательные зависимости и их версии перечисляются явно.
- Linux x86_64 wheel проверяется в чистой среде без установленного Zig; минимальная glibc/manylinux-платформа фиксируется в manifest.
- Кросс-компиляция не заменяет запуск тестов на целевой платформе.

### NFR-4. Наблюдаемость

По контексту и сессии выдавать: время компиляции, время подготовки токенизатора, время accept/mask, число попаданий/промахов/вытеснений кэша, учтённую и пиковую память по категориям, выбранный режим, ошибки и лимиты.

Подробное логирование выключено по умолчанию. Тексты ответов и схем не попадают в логи автоматически. Для разборов расхождений предусмотрен явный режим трассировки с минимальным воспроизводимым примером.

### NFR-5. CI

- На каждый PR: проверка zig fmt, сборка, unit/property/regression-тесты ядра и CPU-интеграции, smoke-тест C ABI и wheel.
- Расширенные fuzz/fault-injection и длительные проверки выполняются по расписанию и перед релизом; результаты сохраняются как артефакты.
- GPU-интеграция обязательна перед релизом на закреплённом GPU-раннере либо по воспроизводимому ручному протоколу с опубликованным результатом.
- Пороговые проверки скорости запускаются на закреплённом оборудовании. Результаты обычного shared CI используются для диагностики, но не для приёмки небольших процентных различий.

## 10. Бенчмарки и критерий полезности

### 10.1. Фиксация окружения

До оптимизаций создать benchmarks/manifest.json со следующими данными:

- CPU, ядра/потоки, RAM, ОС и версия ядра;
- GPU, VRAM, драйвер, CUDA и интерфейс соединения;
- версии Zig, Python, torch, transformers, XGrammar и llguidance, включая commit SHA при сборке из исходников;
- build flags, число потоков, affinity, режимы кэша;
- точные model/tokenizer revisions, dtype, attention backend, KV-cache и состояние compile;
- corpus revision, seed, конфигурации схем и их хэши;
- правила прогрева, повторов, таймаутов и измерения памяти.

Обязательны две среды: CPU-only для ядра/адаптера и GPU end-to-end на одном доступном компьютере. Конкретное железо фиксируется до получения сравнительных результатов. Отсутствие GPU позволяет завершить CPU-проверки, но не заявить GPU-приёмку.

### 10.2. Участники сравнения

1. Актуальные закреплённые XGrammar, включая доступные возможности XGrammar-2.
2. Актуальный закреплённый llguidance.
3. zig-constraints lazy.
4. zig-constraints adaptive.
5. Экспериментальный precompute, если реализован.
6. Реальный Python-callback пользователя, если такой существует; искусственно медленный callback не считается основной базой сравнения.

Все сравнения выполняются на одинаковых токенизаторах и эквивалентных языках/профилях. Если профили JSON различаются, для микробенчмарка задаётся общая грамматика или берётся явно размеченное пересечение. Ограничение функциональности нельзя выдавать за преимущество скорости.

### 10.3. Корпус

- Полный перечень схем выбранной закреплённой версии JSONSchemaBench с отчётом поддержки/отказов.
- Общая поддерживаемая выборка из этого корпуса для корректного сравнения.
- Собственный корпус MVP: закрытые объекты, необязательные поля, массивы, Unicode, длинные строки, вложенность, общие префиксы enum и крупные наборы альтернатив.
- Поток разных схем; повторение одной схемы; смешанный поток с контролируемой долей повторов.
- Сложные и вырожденные примеры: пустые допустимые значения, противоречия, границы лимитов, длинные общие префиксы и плотные/разреженные маски.

Разделить набор настройки эвристик и контрольный набор. Зафиксировать разделение до подбора порогов adaptive. [MaskBench](https://github.com/guidance-ai/jsonschemabench/tree/main/maskbench) использовать как воспроизводимый ориентир; опубликованные таблицы не заменяют локальный прогон.

### 10.4. Матрица измерений

| Кейс | Условия | Метрики |
|---|---|---|
| B1. Подготовка | Новый процесс; отдельно первый tokenizer и новая схема при готовом tokenizer | import/startup, tokenizer prepare, compile, первая маска, peak memory |
| B2. Тёплая схема | Много сессий одной схемы | session create, accept, mask p50/p95/p99/max |
| B3. Смена схем | Уникальные и повторяющиеся схемы в фиксированном порядке | Задержка, hit rate, eviction, memory |
| B4. Батч | 1, 8, 32, 128 сессий; одинаковые и разные схемы | Время всего батча, пропускная способность, потоки |
| B5. Бюджет | 64, 128, 256 MiB общего лимита; допустимые размеры кэша внутри него | Поддерживаемая нагрузка, ResourceLimit, peak allocations |
| B6. Токенизаторы | Реальные закреплённые словари; синтетические 32k/128k/256k отдельно | Время подготовки/маски, память |
| B7. End-to-end | Одна модель 1–3B, batch 1/8/32 в пределах VRAM, max_new_tokens 512 | TTFT, время запроса, output tokens/s, p50/p99 inter-token latency |
| B8. Длительная работа | Не менее 100k суммарных шагов и 10k циклов create/destroy | Плато памяти, корректность, стабильность задержки |

В B7 фиксируется фактическая длина каждого ответа; лимит 512 не означает, что все ответы имеют эту длину. OOM и неподдерживаемые конфигурации отражаются в таблице. Короткие ответы не создают иллюзию ускорения: публикуются длины, tokens/s и время запроса вместе.

### 10.5. Методика времени

- CPU-таймер измеряет компиляцию и ядро отдельно от Python/C ABI.
- Микробенчмарки GPU корректно синхронизируют измеряемые операции; end-to-end не добавляет лишнюю синхронизацию на каждом токене только ради таймера.
- Публиковать время построения маски, её переноса, применения и полный путь, не суммируя перекрывающиеся интервалы как независимую задержку.
- Для сравнения масок использовать одинаковые заранее заданные валидные token traces.
- Для end-to-end сравнивать одинаковую конфигурацию генерации и несколько повторов; идентичность текста не предполагается без доказанного паритета sampling.
- Cold-start: не менее 30 независимых повторов выбранных кейсов; тёплые измерения — не менее 10k наблюдений на класс нагрузки для p99. Правила объединения классов публикуются.
- Отдельно показывать медиану результатов по схемам и распределение по токенам, чтобы длинные простые ответы не скрывали сложные схемы.
- Сохранять сырые результаты и оценку разброса; таймауты и ошибки не исключаются молча.

### 10.6. Цели производительности

До завершения этапа 0 абсолютные микросекунды и обещания 10×/20× не являются обязательствами.

Основная проверяемая гипотеза: на заранее выбранном контрольном сценарии adaptive обеспечивает хотя бы одно из преимуществ относительно лучшего по соответствующей метрике из двух внешних движков:

- снижение p95 времени «новая схема → первая маска» не менее чем на 20%; либо
- снижение сопоставимой пиковой памяти процесса не менее чем на 20% при одинаковой нагрузке и функциональности; либо
- снижение p99 времени построения маски не менее чем на 20%.

Дополнительные условия: остальные измеренные показатели задержки на этом сценарии не ухудшаются более чем на 10% относительно того же выбранного конкурента; все расхождения с другим конкурентом также публикуются. Для end-to-end отсутствие регрессии более 5% относительно выбранного constrained-baseline проверяется с учётом разброса. Это проектные пороги принятия решения, а не прогноз достижимой скорости.

На этапе 0 выбирается один основной сценарий и одна основная метрика для итогового решения; остальные остаются вторичными. Нельзя после тестов выбрать только выигравший пример.

Если преимущества не подтверждены, допустим результат «корректный прототип, гипотеза производительности не подтверждена». Он не называется успешной приёмкой оптимизированного продукта. Возможность продолжать ради встраиваемости оформляется отдельным изменением цели с собственными критериями.

## 11. Тестирование

### T1. Независимый эталон

Разработать простую эталонную реализацию языка MVP, отделённую от оптимизированного ядра. Она не должна использовать тот же кэш или тот же код переходов как единственный источник истины.

На ограниченных грамматиках и малых словарях выполнять исчерпывающий перебор допустимых завершений и сравнение масок. На больших словарях проверять заданные трассы и сгенерированные состояния. Отдельно проверять финальные JSON-документы независимым валидатором Draft 2020-12 и проверкой canonical-v1.

Проверка только готового JSON недостаточна: она не обнаружит ошибочно запрещённые допустимые токены.

### T2. Паритет

- Lazy/adaptive/precompute: побитовое совпадение масок на всём корпусе.
- С включённым/выключенным кэшем, вытеснениями и разным числом потоков результат одинаков.
- Между движками: сравнение на общем точно определённом языке; разница в профилях сначала классифицируется, затем исправляется тестовый контракт или реализация.
- Для каждого расхождения сохранять схему, профиль, tokenizer revision, token IDs префикса и различающиеся биты.

### T3. Граничные случаи

Обязательны: vocab не кратен 32, пустой батч, недопустимый ID, маленький выходной буфер, повторный EOS, PAD в активной сессии, токен с несколькими структурными символами, незавершённый UTF-8, escapes на границах токенов, пустая строка, enum с общими префиксами, необязательные ключи, число перед разделителем, минимальные/максимальные длины, пустое множество продолжений.

Проверить эквивалентность полного декодирования и модели байтов адаптера для зарегистрированных токенизаторов, включая added/special tokens. Проверить недопустимые последовательности и отказ неподдерживаемым decoder-настройкам.

### T4. Fuzz и fault injection

- Не менее 1 млн суммарных fuzz-итераций по входным схемам, токенам и последовательностям API-вызовов на валидных выделенных буферах.
- Отдельные кампании: компилятор, accept/mask, кэш, C/Python-граница.
- Инъекция отказа allocator в каждой проверяемой точке выделения: штатная ошибка, корректное освобождение и отсутствие частичного принятия токена.
- Негативные тесты ABI не разыменовывают произвольные адреса из чисел; неверные размеры тестируются на реально существующих буферах.
- Сохранять corpus, crash reproducers, seed и доступные данные покрытия. Число итераций не считается доказательством отсутствия всех ошибок.

### T5. Интеграция

Проверить CPU и CUDA, greedy/sampling, смешанный батч, left padding, ранний EOS, лимит длины, отмену, освобождение после ошибки, конфликты processors, отсутствие модуля и неподдерживаемые режимы.

Особенно проверить, что запрет не снимается последующим processor и что завершающий токен отражён в состоянии сессии. Не требовать равенства обычной генерации и constrained generation: у них разные допустимые распределения.

### T6. Упаковка

Установка wheel и импорт в чистой среде; поддерживаемые версии CPython; работа нативного ядра без torch; установка integration extra; C-пример без Python; проверки экспортируемого ABI.

|---|---|---|

Ориентир этапа 0 — 5–10 рабочих дней при наличии стенда. Сроки остальных этапов оцениваются после него по фактической сложности токенизаторов, семантики и состояния парсера. Календарный срок не служит основанием сокращать проверки корректности.

Go/No-Go — технический результат проверки гипотезы. No-Go не означает отсутствие полезных артефактов: код прототипа, тесты и результаты измерений сохраняются.

## 13. Приёмка

### 13.1. Инженерная приёмка MVP

1. Реализованы требования, помеченные MVP, и опубликована точная таблица поддержки.
2. Все маски проходят эталонные и межрежимные проверки; нет известных необъяснённых расхождений.
3. Все ответы с completed=true на корпусе валидны по исходной поддерживаемой схеме и профилю.
4. UnsupportedFeature, ResourceLimit и прерывания не переводятся в незаметную генерацию без ограничений.
5. Учёт памяти охватывает все выделения ядра; выдерживаются настроенные лимиты и испытания жизненного цикла.
6. Пройдены fuzz, fault injection и интеграционные проверки; обнаруженные ошибки исправлены либо соответствующая возможность явно исключена из заявленной поддержки до релиза.
7. C ABI, Python wheel и adapter работают в закреплённой матрице; есть пример запуска без Python.
8. Опубликованы воспроизводимые сравнения с обоими внешними движками, включая проигранные кейсы, ограничения и сырые данные.

### 13.2. Приёмка продуктовой гипотезы

Отдельно выполнен критерий раздела 10.6 на заранее выбранном контрольном сценарии. Положительный результат инженерной приёмки без этого критерия означает корректный прототип, но не подтверждённое преимущество новой реализации.

## 14. Риски и действия

| Риск | Действие |
|---|---|
| Дублирование уже доступных оптимизаций XGrammar-2/llguidance | Измерить закреплённые актуальные версии до расширения реализации |
| Различия JSON Schema и языка генерации | Явный canonical-v1, таблица исключений, независимый валидатор и тесты полноты |
| Неверное байтовое представление токенов | Сертифицировать конкретные адаптеры, отклонять остальные |
| Кэш ускоряет среднее, но увеличивает хвост задержки или память | Жёсткий бюджет, измерение p99/max, lazy как точный путь при промахе |
| Ошибочный ключ кэша между схемами | Полный контекст идентичности, проверка коллизий, cross-schema тесты |
| CPU-ускорение не влияет на время ответа | Измерять полный GPU-путь и фактическое перекрытие |
| Сложность Python/GIL и ABI | Небольшой мост, владельцы буферов, тесты времени жизни и конкуренции |
| Изменения Zig или внутренних API HF | Закреплённые версии, отдельные обновления с повторной проверкой |
| Полное переписывание оказывается дороже полезного результата | Ранние baseline и Go/No-Go; не расширять roadmap до проверки ценности |
