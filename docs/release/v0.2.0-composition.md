# Release 0.2.0: composition and split of the working tree

Machine-readable form: [v0.2.0-composition.json](v0.2.0-composition.json),
checked by `.github/scripts/release_gate.py` in the release workflow and
by `tests/test_release_manifest.py`. The owner decides the scope (rework
spec C7). The release line holds this composition (2026-10-09: the
release-line patch, then the release paths and the partial edits below;
2026-10-10: squashed into one commit on top of `v0.1.0` for the public
preview, with a history-independent manifest; 2026-10-11: repinned for
the Zig 0.17.0 migration and the CPython 3.12-3.15 preparation
(`Py_LIMITED_API=0x030C0000`, abi3 floor `cp312`); the R6 verdict on
record still names `6e62e0d1` only and the gate stays closed until the
next acceptance names these sources).

## Why a split is needed

The accepted core is the one the R6 review admitted (`6e62e0d1...`): the
line that passed the T3 coverage acceptance plus the release-line fix of
the open-object certificates and the `-Dstrip` build option. The wave-2
working tree also held features that change the core, the C header and
the Python bindings: T9 (rollback, draft validation), T12 (regex
constraint), T13 (platforms) and T14 (Metaspace). The new
`python/bolorgir/_core.c` calls `blg_session_create_ex`,
`blg_session_rollback` and `blg_validate_tokens`, which the accepted core
does not export; pairing them with it would fail at import. Release 0.2.0
therefore carries the core and the bindings exactly as accepted, and the
wave-2 features stay for a later line with their own acceptance.

For the public preview the line was squashed into one commit on top of
`v0.1.0` (2026-10-10): the preparation commits are not part of the
published history, so the check below pins the accepted files per file by
git blob id instead of comparing against a base revision. The 2026-10-11
toolchain update keeps the split (no wave-2 files) and repins the touched
files; the accepted preview artifacts keep their record in the evidence
of `6e62e0d1`.

The exact path lists are `release_paths`, `partial_paths`, `core.manifest`,
`bindings.manifest` and `later_line_absent` in the JSON.

Build flags: `-Drelease=true -Dstrip=true -Dtarget=x86_64-linux-gnu.2.28
-Dcpu=baseline` with Zig 0.17.0. `-Dstrip=true` drops the debug sections,
which embed absolute source and cache paths; with them two builds of the
same sources differ (only in `.debug_line` and `.debug_str`), without them
they are byte-identical. The candidate is built twice in different
directories and the two libraries must compare equal (`cmp`); the
acceptance and the measurements run on those bytes, and the release
workflow builds the same bytes, which the gate checks by hash. A debug
build for diagnosis is a separate artifact, never the measured one.

## Later line (wave 2)

`later_line_paths` in the JSON lists the paths of the wave-2 work:
`src/` changes and `src/regex.zig`, `include/bolorgir.h`,
`python/bolorgir/_core.c`, `python/bolorgir/tokenizers.py`, the
T9/T12/T13/T14 tests and tools, the platform workflows, ADR-0013 to
ADR-0017, `docs/API.md` and `docs/supported_features.md`.
`later_line_absent` is the subset of that list which must not appear in
the release tree at all (the files the later line adds); the paths that
exist in the release tree in their accepted form are pinned by the
manifests and listed for the later line only. That line needs its own
builds, tests, T9 overhead check and, when it changes the masks, a new
acceptance.

## How the line is checked

`release_gate.py sources` (the `line` job of the release workflow) reads
`core.manifest` and `bindings.manifest` and needs no git history: every
pinned file must be present in the checked-out tree with the pinned git
blob id (`git hash-object`), no extra file may sit under the core paths
of `core.paths`, and no path of `later_line_absent` may be present. A
different edit of a pinned file, an added file under `src/` or
`include/`, a missing file, or a wave-2 file fails it. Should the
release-line patch change after review, the pins of the manifest change
with it.

`release_gate.py abi --base-only` additionally requires the bindings to
call only the functions of the base ABI; `release_gate.py abi --lib
<lib>` checks the built core exports every function the bindings call.
The line was prepared on a branch from the accepted revision (2026-10-09)
and squashed onto `v0.1.0` for the preview (2026-10-10); the manifests
were repinned for the Zig 0.17.0 migration (2026-10-11).

## Gate of the final tag

`gate.r6_acceptance` and `gate.t8a_report` in the JSON stay `null` until
the owner records the committed R6 review verdict
(`benchmarks/coverage/spec-v1/<label>/review/acceptance.json`) and the T8a
report. The `gate` job refuses a final tag unless both are positive and
name the core that the workflow built. Release candidates and manual
builds do not need the gate. Their core artifact carries
`release-status.txt` with the word PRELIMINARY. Publishing to PyPI also
needs the owner's consent (T7b, the `pypi` environment reviewers).
