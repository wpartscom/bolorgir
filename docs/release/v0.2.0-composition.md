## Where the split stands

The accepted core of record for the earlier composition is the one the
R6 review admitted (`6e62e0d1...`): the line that passed the T3 coverage
acceptance plus the release-line fix of the open-object certificates and
the `-Dstrip` build option. Everything in this composition now sits on
top of that core, and the additions change it:

- T9 (ADR-0014): `blg_session_create_ex`, `blg_session_rollback`,
  `blg_validate_tokens`; the bindings call them, so a package of this
  line needs a core that exports them. The three symbols are part of the
  base ABI of this composition (`abi.base_functions`), and
  `abi.later_line_functions` is empty.
- T12 (ADR-0015): `BLG_CONSTRAINT_REGEX` and `src/regex.zig`.
- T10 (ADR-0016): the `bolorgir.vllm` adapter, the pinned vLLM patch in
  `integrations/vllm/` and the observation/collector material of the
  agent evaluation.

Because the core changed, the old R6 verdict and the old preview binding
do not transfer: `preview.r6_acceptance` stays as the historical
`6e62e0d1` binding, the gate fields stay `null` until the owner sets them
after the gates close (T8a is still open), and the admitted
`t3-9a5baf3e/review-2` verdict (2026-10-13) names that earlier core, not
the sources of this composition: the mask, state-copy and
certificate-cache changes came after it. On 2026-10-26 the core and
bindings manifests were repinned to the publication tree (including the
new `src/diag.zig`), which restores the `sources` gate for these sources
only. A repin is not an acceptance: the current tree still needs its own
R6 verdict and its T8a run before any gate field can be set, and
launching the next public preview (planned as `0.2.0rc2`) stays with the
owner.

For the public preview the line was squashed into one commit on top of
`v0.1.0` (2026-10-10): the preparation commits are not part of the
published history, so the check below pins the accepted files per file by
git blob id instead of comparing against a base revision.

The exact path lists are `release_paths`, `partial_paths`, `core.manifest`,
`bindings.manifest` and `later_line_absent` in the JSON. `partial_paths`
is empty: the files that were previously transferred by hand (the
bindings, `CHANGELOG.md`, `docs/README.md`) now ship as they are in the
working tree.

Build flags: `-Drelease=true -Dstrip=true -Dtarget=x86_64-linux-gnu.2.28
-Dcpu=baseline` with Zig 0.17.0. `-Dstrip=true` drops the debug sections,
which embed absolute source and cache paths; with them two builds of the
same sources differ (only in `.debug_line` and `.debug_str`), without them
they are byte-identical. The candidate is built twice in different
directories and the two libraries must compare equal (`cmp`); the
acceptance and the measurements run on those bytes, and the release
workflow builds the same bytes, which the gate checks by hash. A debug
build for diagnosis is a separate artifact, never the measured one.

## Later line

`later_line_paths` (identical to `later_line_absent` now) lists the paths
that are not implemented in this line and must not appear in the release
tree: ADR-0013 (interop numbers), ADR-0017 (bounded whitespace), the
platform workflows (T13) and the tokenizer survey/Metaspace work (T14).
They come with their own decisions, builds, tests and acceptance when
that work starts; nothing of this line depends on them.

## How the line is checked

`release_gate.py sources` (the `line` job of the release workflow) reads
`core.manifest` and `bindings.manifest` and needs no git history: every
pinned file must be present in the checked-out tree with the pinned git
blob id (`git hash-object`), no extra file may sit under the core paths
of `core.paths`, and no path of `later_line_absent` may be present. A
different edit of a pinned file, an added file under `src/` or
`include/`, a missing file, or a later-line file fails it. Should the
core change after review, the pins of the manifest change with it.

`release_gate.py abi --base-only` additionally requires the bindings to
call only the functions of the base ABI; the T9 session functions are
base functions of this composition by decision, so the check passes on
this tree. `release_gate.py abi --lib <lib>` checks the built core
exports every function the bindings call.

## Gate of the final tag

`gate.r6_acceptance` and `gate.t8a_report` in the JSON stay `null` until
the owner records the committed R6 review verdict
(`benchmarks/coverage/spec-v1/<label>/review/acceptance.json`) and the T8a
report for the core of these sources. The `gate` job refuses a final tag
unless both are positive and name the core that the workflow built.
Release candidates and manual builds do not need the gate; their core
artifact carries `release-status.txt` with the word PRELIMINARY. The
`preview` check of an rc tag requires an admitted R6 verdict bound to
the core the workflow built; the committed `6e62e0d1` verdict keeps the
rc1 record and does not qualify the current core. Publishing to PyPI
also needs the owner's consent (T7b, the `pypi` environment reviewers).
