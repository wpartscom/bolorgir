# semantics.md - normative semantics of the canonical-v1 profile

Status: **normative document**. Fixes the document language that the Bolorgir
engine generates and accepts in the MVP. Any divergence of the implementation from this
file is an implementation error; a semantics change is made by editing this file
before changing code. Based on SPEC FR-1..FR-4; the schema acceptance rules are in
docs/supported_features.md §1.

The profile is specified at compile time as `"canonical-v1"` (the default value).
The separate `spec-v1` profile is defined in docs/semantics-spec-v1.md; nothing in
it changes canonical-v1.

## 1. Document language: general structure

A document is a single JSON object, array, string, number, `true`, `false` or `null`,
generated by the rules below from the compiled schema.

- Whitespace outside strings is absent entirely: between any
  structural tokens there are no spaces, tabs or newlines.
- Object keys follow the declaration order in the schema `properties`; declaration
  order is preserved when reading the schema (a JSON document with duplicate
  keys is rejected by the compiler as InvalidSchema).
- Optional keys may be skipped; skipped keys preserve
  the relative order of the remaining ones (see §5).
- Repeating a key in a document is impossible by construction.
- Content after the end of the root value is forbidden: a byte with an empty parse
  stack - error. EOS is accepted only in an accepting state (§8).

## 2. Strings

String: `"` content `"`.

### 2.1. Unescaped content

- Raw bytes >= 0x20, except `"` (0x22) and `\` (0x5C).
- Multibyte UTF-8 sequences are passed raw and validated by the DFA of §3.
- Raw bytes < 0x20 (control) inside a string - parse error.
- Byte 0x7F is allowed raw (it is not a control character in JSON).
- Escaping `/` is **forbidden**: the escape `\/` is not accepted.

### 2.2. Escape table (the only allowed one)

| Character | Code | Mandatory notation |
|---|---|---|
| `"` | 0x22 | `\"` |
| `\` | 0x5C | `\\` |
| backspace | 0x08 | `\b` |
| form feed | 0x0C | `\f` |
| newline | 0x0A | `\n` |
| carriage return | 0x0D | `\r` |
| tab | 0x09 | `\t` |
| other control characters: 0x00-0x07, 0x0B, 0x0E-0x1F | - | `\u00xx`, where `xx` are two **lowercase** hex digits (0-9a-f) of the character code |

Rules:

- The form `\u00xx` is exactly that: after `\u` two zeros are mandatory, then two lowercase
  hex digits forming a code < 0x20 that has no short escape in the table.
- Any other escape - parse error: `\/`, `\'`, `\u0041` (not a control character),
  `\u001B` (uppercase hex), `\u0009` (0x09 must be written `\t`), `\U`, `\xNN` etc.
  Note that `\u000b` is valid: 0x0B has no short escape.
- Codes >= 0x20 in the `\uXXXX` form are forbidden in this profile entirely: arbitrary
  alternative Unicode escapes are not accepted, non-ASCII characters are written raw
  in UTF-8.
- An escape sequence counts as one character when computing the length.

### 2.3. String length

- `minLength`/`maxLength` count Unicode scalar values of the decoded
  value: ASCII byte = 1; completed multibyte character = 1; completed
  escape (short or `\u00xx`) = 1.
- The counter is incremented when a character completes; exceeding `maxLength` on
  increment - parse error (the token is rejected).
- The closing quote is accepted only when `count >= minLength`.
- Absence of `maxLength` means no semantic upper bound;
  engine resource limits are a separate mechanism (see supported_features.md).

## 3. UTF-8

- String values are UTF-8; completed values must contain only
  valid Unicode scalar values (no surrogates U+D800..U+DFFF, no codes
  > U+10FFFF, no overlong encodings).
- The check is a finite automaton over bytes. State: `rem` (0..3) - the number
  of remaining continuation bytes and the range `[lo,hi]` for the next byte:
  - `rem = 0`: byte 0x00-0x7F - character complete;
    0xC2-0xDF → `rem=1, [80,BF]`; 0xE0 → `rem=2, [A0,BF]`;
    0xE1-0xEC, 0xEE, 0xEF → `rem=2, [80,BF]`; 0xED → `rem=2, [80,9F]`;
    0xF0 → `rem=3, [90,BF]`; 0xF1-0xF3 → `rem=3, [80,BF]`;
    0xF4 → `rem=3, [80,8F]`. Other bytes (0x80-0xC1, 0xF5-0xFF) - error.
  - `rem > 0`: a byte in `[lo,hi]` → `rem -= 1`; if `rem > 0` the range
    resets to `[80,BF]`; if `rem == 0`, the character is complete. A byte outside
    the range - error.
- An incomplete UTF-8 sequence is allowed **only** as an intermediate
  state between tokens (a token may end in the middle of a character).
- A closing quote with `rem > 0` - error: a finished document with
  an incomplete sequence is invalid.

## 4. Numbers

### 4.1. integer

Grammar: `-?(0|[1-9][0-9]*)`.

- Leading zeros are forbidden: `01` is not accepted.
- The notation `-0` is grammatically allowed at the document level but is never
  produced by enum/const normalization (see §6).
- Decimal notation without a fraction and without an exponent - always.

### 4.2. number

Grammar: integer part, then optionally `.` [0-9]+, then optionally
`[eE][+-]?[0-9]+`.

- Complete states: after the integer-part digits; after a fraction digit;
  after an exponent digit.
- Incomplete forms (`1.`, `1e`, `1e+`) are not valid documents.
- `NaN`, `Infinity`, `-Infinity` are not JSON numbers and are forbidden.

### 4.3. Lazy number completion

A byte that is not a continuation of the number in a complete state completes the number
and is reprocessed by the parent construct (a separator, a closing
bracket etc.). In a non-complete state such a byte - parse error.

## 5. Objects: key order and the candidate rule

For an object node with properties `props[0..n)` (declaration order) and a
set of required ones:

- Keys go strictly in `props` order. Optional keys may be skipped;
  a skipped key cannot be returned.
- The object automaton stores `idx` - the index of the first unresolved property, and
  `cur` - the index of the selected property; phases: open | key | value | sep.
  - open: expects `{` → phase key.
  - key: on byte `"` the candidate set - all `props[i]`, `i >= idx`,
    such that all `props[j]`, `idx <= j < i`, are optional. Each
    candidate spawns a separate parse branch with literal `"key_i":`
    (the key is serialized per the table of §2.2). On byte `}` the object completes,
    only if all `props[j]`, `j >= idx`, are optional (no required
    left). Any other byte - error.
  - value: after the key literal the value of property `cur` is parsed.
  - sep: `idx = cur + 1`; `,` → key phase after the comma; `}` → completion when
    there is no required `j >= idx`; otherwise - error.
- A comma in the sep phase is allowed only if properties are left
  (`idx < n`); after a comma a key is mandatory: `}` right after a comma - error.
  **Trailing comma is forbidden always** - in objects and arrays (§7).
- Corollary: candidates at the key position are either the nearest required key or
  any optional key up to and including it. The rule constructively
  excludes the dead end "required key skipped": a branch leading to such a dead end
  is never spawned.

## 6. enum/const normalization (exact decimal)

`const` is equivalent to `enum` of one value; specifying `enum` and `const`
at the same time in one schema - InvalidSchema (and not set intersection).
Every value is serialized by the compiler into a literal alternative:

- string → canonical JSON literal per the table of §2.2;
- boolean/null → `true` / `false` / `null`;
- numbers → exact decimal normalization of the schema lexeme **without binary64**:
  the lexeme is parsed into a decimal fraction (mantissa + decimal exponent as a
  rational number). Representability limit: at most 400 significant digits
  and |written exponent| <= 400; overflow - InvalidSchema.

Number notation rules:

1. Zero in any notation - `0`: **`-0` → `0`**, `-0.0` → `0`, `-0e7` → `0`.
   The minus sign of zero is not preserved.
2. If the value is integral - decimal integer notation without a fraction and
   exponent, per the grammar of §4.1.
3. A non-integral value written without an exponent - `int.frac` notation: strip
   leading zeros of the integer part down to one digit; strip trailing zeros of the
   fraction.
4. A non-integral value written with an exponent - the scientific form is **preserved**:
   the mantissa stays as in the schema with the zero normalization of item 3 (a fraction
   emptied after trailing-zero removal is dropped together with the dot),
   the exponent is normalized: `E` → `e`, no `+`, no leading zeros. The notation
   always matches the grammar of §4.2.

Examples:

| Schema lexeme | Value | Canonical notation |
|---|---|---|
| `1e2` | 100 | `100` |
| `1.50` | 3/2 | `1.5` |
| `0.1e1` | 1 | `1` |
| `-0` | 0 | `0` |
| `1.5e1` | 15 | `15` |
| `1E+2` | 100 | `100` |
| `12.340e0` | 12.34 | `12.34e0` |
| `1e-3` | 0.001 | `1e-3` |
| `1.5e-3` | 0.0015 | `1.5e-3` |
| `1.50E-3` | 0.0015 | `1.5e-3` |
| `10e-3` | 0.01 | `10e-3` |
| `-0.50` | -1/2 | `-0.5` |
| `10.0` | 10 | `10` |

Filtering and duplicates:

- Every enum value is checked against `type` and `minLength`/`maxLength`;
  incompatible values are dropped. If none is left -
  UnsatisfiableConstraint.
- Number comparison is exact by rational value, without rounding through
  binary64.
- Duplicate values after normalization are removed.
- enum without an explicit `type`: the type is inferred from the values (all values of
  one type; a mixed enum - UnsupportedFeature in the MVP).

## 7. Arrays

- `items` - one schema for all elements (mandatory for `array`).
- `minItems`/`maxItems` - non-negative integers; `minItems > maxItems` -
  UnsatisfiableConstraint. Absence of `maxItems` - no semantic
  upper bound (internally UNBOUNDED).
- Automaton: open (`[`) → body: if `count >= max` - only `]`; `]` completes
  when `count >= min`, otherwise error; after an element - sep: `,` → the next
  element (if `count >= max` - error), `]` → completion when `count >= min`.
- After a comma an element is mandatory: `]` right after a comma - error.
  **Trailing comma is forbidden always** (as in objects, §5).
- Repetitions are represented by a counter; a large `maxItems` is not expanded into
  grammar copies.

## 8. Document completion

- EOS is allowed only in an accepting state: the parse stack is empty or
  the cascade "top - number in a complete state" virtually collapses to
  an empty stack without reading bytes.
- With several registered EOS IDs the rules are the same for all.
- A repeated EOS after an accepted EOS: the state stays accepting, accept
  succeeds, the document does not change (finalization - `finish`).
- A correct prefix is not passed off as a finished document: `finish` requires
  an accepting state.

## 9. FR-3: literal alternatives

- Input: a JSON array of UTF-8 strings (already decoded values, without
  JSON escaping). The list is non-empty.
- Duplicates are removed. An empty string is allowed as a variant (a literal of length 0,
  completes instantly).
- A valid answer - exactly one string from the list in full, raw bytes without
  quotes and escaping.
- Common prefixes of alternatives, Unicode and tokens spanning several
  characters are supported (each alternative - a separate parse branch).
- The format is not mixed with arbitrary regex.

## 10. Completeness and absence of dead ends

**Claim.** After the compile-time checks (docs/supported_features.md §1, enum filtering
§6, min<=max checks, $ref acyclicity, depth limit) any parse state
that is not an error can continue to a valid finished document.

**Argument by construction** (induction over the parse stack):

1. *String.* From any correct string state (normal/escape/`\u00xx`,
   counter <= max) a continuation to closing exists: if `count < min`,
   characters `'a'` are added (each valid, UTF-8 DFA at rem=0, min
   is finite); escape states complete within <= 3 bytes per the table of §2.2;
   an incomplete UTF-8 sequence is completed by continuation bytes from the current range.
   After `count >= min` and `rem == 0` the closing `"` is accepted. maxLength does not
   interfere: a state with `count > max` was rejected on increment and is absent
   among live states.
2. *Number.* In a complete state the number completes "lazily" on any
   parent separator (§4.3). In a non-complete state a continuation always
   exists: after `-` - a digit, after `.` - a digit, after `e`/`e+`/`e-` - a digit;
   a digit moves to the complete state.
3. *Array.* If `count >= min`, `]` is allowed; if `count < min`, then
   `count < max` (otherwise the state would have been rejected) and the next
   element is allowed; an element is a schema to which the induction applies. min/max are finite
   or max = UNBOUNDED, so `min` is reachable in a finite number of elements.
4. *Object.* The candidate rule of §5 guarantees: in the key phase either `}` is allowed
   (no required left), or among the candidates there is the nearest required key,
   and its choice is not blocked. Skipping a required key is impossible by
   construction. Property values are schemas to which the induction applies. The number
   of properties is finite.
5. *enum/const.* After the filtering of §6 the alternative set is non-empty (otherwise
   UnsatisfiableConstraint at compile time); each alternative is
   a finite literal.
6. *choice.* At least one branch is alive - otherwise the state would be a parse error
   (a branch is dropped on the first unaccepted byte). A live branch can continue
   by induction.
7. *$ref.* The reference graph is acyclic (checked at compile time), so the expansion
   of references is finite and reduces to a finite tree of constructs.

**Corollaries.**

- The construction guarantees byte-wise completability: from any non-error
  state a continuation to a full document exists. For the MASK this is
  sufficient only with full byte coverage of the vocabulary (all 256
  single-byte tokens): then any byte continuation can be fed
  with single-byte tokens, and no runtime filter is needed.
- With an incomplete vocabulary, mask safety is provided by the completion filter for
  finite literal languages (SPEC 3.1, src/complete.zig): a token
  is allowed only if completion is reachable after it; a dead-end token does not
  enter the mask, and `accept` of such a token - INVALID_TOKEN without changing
  the state. For open classes (str/int/num/repeat) with an incomplete vocabulary
  the conservative compile-time segmentability check applies
  (docs/DESIGN.md §4, docs/supported_features.md §5).
- A dead end is possible only in a degenerate case: no vocabulary token and no
  EOS is accepted by the current state (e.g. the vocabulary does not cover the
  mandatory next byte). Then the engine returns DeadEnd with the state and the
  cause; automatically allowing the whole vocabulary or EOS is forbidden (SPEC FR-4).

## 11. Differences between canonical-v1 and full JSON / JSON Schema

canonical-v1 is an explicit narrowing of representations. The following documents are valid per
RFC 8259 and/or the original JSON Schema, but **are not part** of the canonical-v1 language:

1. Exponential notation of an integral value for `type: integer` (`1e2`, `1E+2`,
   `10e0`): allowed by the original JSON Schema as an integer, but the canonical-v1
   integer language - only decimal notation without an exponent (`100`).
2. Fractional notation of an integral value for `type: integer` (`100.0`, `100.00`):
   not part of the integer language.
3. Whitespace outside strings: `{ "a": 1 }`, indentation, newlines - outside the language;
   serialization is always compact.
4. Alternative string escapes: `\/`, `\u0041`, `\u001B` (uppercase hex),
   `\u0009` instead of `\t`, `\uXXXX` for codes >= 0x20 - forbidden; exactly the
   table of §2.2 is allowed.
5. A key order different from the declaration order in `properties` - outside the language,
   even if JSON Schema does not restrict the order.
6. Keys not declared in `properties` (`additionalProperties` in the MVP is always
   `false`) - outside the language.
7. Skipping a required key - outside the language by construction (§5); the full JSON Schema
   allows any order and presence/absence of optional keys in any
   order.
8. `NaN`, `Infinity`, `-Infinity`, hexadecimal numbers, leading zeros,
   `+1`, `.5`, `1.` - not JSON numbers and outside the language.
9. JSON Schema capabilities outside the FR-1 profile (`anyOf`/`oneOf`/`allOf`/`not`,
   `minimum`/`maximum`/`multipleOf`, `pattern`/`format`, `uniqueItems`,
   boolean schemas, external `$ref` etc.) do not define a language: such schemas
   are rejected by the compiler with UnsupportedFeature before generation, rather than
   "weakened".

Completeness is claimed only relative to the canonical-v1 language: the engine does not forbid
any document of this language for a supported schema (SPEC §3.2). Completeness
relative to all serializations allowed by the original JSON Schema is not claimed;
differences are reflected in the compiler report and tests.
