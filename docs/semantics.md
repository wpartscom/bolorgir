# semantics.md — нормативная семантика профиля canonical-v1

Статус: **нормативный документ**. Фиксирует язык документов, который порождает и
принимает движок zig-constraints в MVP. Любое расхождение реализации с этим
файлом — ошибка реализации; изменение семантики оформляется правкой этого файла
и docs/DESIGN.md до изменения кода. Основано на ТЗ FR-1..FR-4 и docs/DESIGN.md §1.

Профиль указывается при компиляции как `"canonical-v1"` (значение по умолчанию).
Других профилей в MVP нет.

## 1. Документный язык: общая структура

Документ — один JSON-объект, массив, строка, число, `true`, `false` или `null`,
порождённый по правилам ниже из скомпилированной схемы.

- Пробельные символы вне строк отсутствуют полностью: между любыми
  структурными токенами нет ни пробелов, ни табуляций, ни переводов строк.
- Ключи объектов следуют порядку объявления в `properties` схемы; порядок
  объявления сохраняется при чтении схемы (документ JSON с повторяющимися
  ключами отклоняется компилятором как InvalidSchema).
- Необязательные ключи можно пропускать; пропущенные ключи сохраняют
  относительный порядок оставшихся (см. §5).
- Повторение ключа в документе невозможно по построению.
- Контент после конца корневого значения запрещён: байт при пустом стеке
  разбора — ошибка. EOS принимается только в принимающем состоянии (§8).

## 2. Строки

Строка: `"` содержимое `"`.

### 2.1. Неэкранированное содержимое

- Raw-байты >= 0x20, кроме `"` (0x22) и `\` (0x5C).
- Многобайтовые UTF-8-последовательности передаются raw и валидируются DFA §3.
- Raw-байты < 0x20 (управляющие) внутри строки — ошибка разбора.
- Байт 0x7F допустим raw (он не является управляющим по JSON).
- Символ `/` экранировать **запрещено**: escape `\/` не принимается.

### 2.2. Таблица экранирования (единственная допустимая)

| Символ | Код | Обязательная запись |
|---|---|---|
| `"` | 0x22 | `\"` |
| `\` | 0x5C | `\\` |
| backspace | 0x08 | `\b` |
| form feed | 0x0C | `\f` |
| newline | 0x0A | `\n` |
| carriage return | 0x0D | `\r` |
| tab | 0x09 | `\t` |
| прочие управляющие: 0x00–0x07, 0x0B, 0x0E–0x1F | — | `\u00xx`, где `xx` — две **строчные** hex-цифры (0-9a-f) кода символа |

Правила:

- Форма `\u00xx` — ровно такая: после `\u` обязаны два нуля, затем две строчные
  hex-цифры, образующие код < 0x20, не имеющий короткого escape из таблицы.
- Любой другой escape — ошибка разбора: `\/`, `\'`, `\u0041` (не управляющий),
  `\u001B` (hex верхнего регистра), `\u000b` (есть короткий `\b`? — нет:
  0x0B короткого escape не имеет, запись `\u000b` допустима; но `\u0009`
  запрещён, т.к. для 0x09 обязателен `\t`), `\U`, `\xNN` и т.п.
- Коды >= 0x20 в форме `\uXXXX` запрещены в этом профиле вообще: произвольные
  альтернативные Unicode-escapes не принимаются, не-ASCII символы пишутся raw
  в UTF-8.
- Escape последовательность целиком считается одним символом при подсчёте длины.

### 2.3. Длина строки

- `minLength`/`maxLength` считаются в Unicode scalar values декодированного
  значения: ASCII-байт = 1; завершённый многобайтовый символ = 1; завершённый
  escape (короткий или `\u00xx`) = 1.
- Счётчик инкрементируется при завершении символа; превышение `maxLength` при
  инкременте — ошибка разбора (токен отклоняется).
- Закрывающая кавычка принимается только при `count >= minLength`.
- Отсутствие `maxLength` означает отсутствие семантического верхнего предела;
  ресурсные лимиты движка — отдельный механизм (см. supported_features.md).

## 3. UTF-8

- Строковые значения — UTF-8; завершённые значения обязаны содержать только
  валидные Unicode scalar values (без суррогатов U+D800..U+DFFF, без кодов
  > U+10FFFF, без overlong-записей).
- Проверка — конечный автомат над байтами. Состояние: `rem` (0..3) — число
  оставшихся continuation-байтов и диапазон `[lo,hi]` для следующего байта:
  - `rem = 0`: байт 0x00–0x7F — символ завершён;
    0xC2–0xDF → `rem=1, [80,BF]`; 0xE0 → `rem=2, [A0,BF]`;
    0xE1–0xEC, 0xEE, 0xEF → `rem=2, [80,BF]`; 0xED → `rem=2, [80,9F]`;
    0xF0 → `rem=3, [90,BF]`; 0xF1–0xF3 → `rem=3, [80,BF]`;
    0xF4 → `rem=3, [80,8F]`. Прочие байты (0x80–0xC1, 0xF5–0xFF) — ошибка.
  - `rem > 0`: байт в `[lo,hi]` → `rem -= 1`; если `rem > 0`, диапазон
    сбрасывается в `[80,BF]`; если `rem == 0`, символ завершён. Байт вне
    диапазона — ошибка.
- Незавершённая UTF-8-последовательность допустима **только** как промежуточное
  состояние между токенами (токен может заканчиваться в середине символа).
- Закрывающая кавычка при `rem > 0` — ошибка: завершённый документ с
  незавершённой последовательностью недопустим.

## 4. Числа

### 4.1. integer

Грамматика: `-?(0|[1-9][0-9]*)`.

- Ведущие нули запрещены: `01` не принимается.
- Запись `-0` грамматически допустима на уровне документа, но никогда не
  порождается нормализацией enum/const (см. §6).
- Десятичная запись без дробной части и без экспоненты — всегда.

### 4.2. number

Грамматика: integer-часть, затем опционально `.` [0-9]+, затем опционально
`[eE][+-]?[0-9]+`.

- Complete-состояния: после цифр целой части; после цифры дробной части;
  после цифры экспоненты.
- Незавершённые формы (`1.`, `1e`, `1e+`) не являются допустимыми документами.
- `NaN`, `Infinity`, `-Infinity` не являются JSON-числами и запрещены.

### 4.3. Ленивое завершение числа

Байт, не являющийся продолжением числа в complete-состоянии, завершает число
и переобрабатывается родительской конструкцией (разделитель, закрывающая
скобка и т.п.). В не-complete состоянии такой байт — ошибка разбора.

## 5. Объекты: порядок ключей и правило кандидатов

Для объектного узла со свойствами `props[0..n)` (порядок объявления) и
множеством required:

- Ключи идут строго в порядке `props`. Необязательные ключи можно пропускать;
  пропущенный ключ вернуть нельзя.
- Автомат объекта хранит `idx` — индекс первого неразрешённого свойства, и
  `cur` — индекс выбранного свойства; фазы: open | key | value | sep.
  - open: ожидает `{` → фаза key.
  - key: при байте `"` множество кандидатов — все `props[i]`, `i >= idx`,
    такие что все `props[j]`, `idx <= j < i`, — необязательные. На каждого
    кандидата порождается отдельная ветвь разбора с литералом `"key_i":`
    (ключ сериализуется по таблице §2.2). При байте `}` объект завершается,
    только если все `props[j]`, `j >= idx`, необязательные (не осталось
    required). Иной байт — ошибка.
  - value: после литерала ключа разбирается значение свойства `cur`.
  - sep: `idx = cur + 1`; `,` → фаза key после запятой; `}` → завершение при
    отсутствии required `j >= idx`; иное — ошибка.
- Запятая в фазе sep допустима, только если остались непройденные свойства
  (`idx < n`); после запятой ключ обязателен: `}` сразу после запятой — ошибка.
  **Trailing comma запрещён всегда** — и в объектах, и в массивах (§7).
- Следствие: кандидаты в позиции ключа — это либо ближайший required-ключ, либо
  любой необязательный ключ до него включительно. Правило конструктивно
  исключает тупик «пропущен required-ключ»: ветвь, ведущая к такому тупику,
  не порождается никогда.

## 6. Нормализация enum/const (точная десятичная)

`const` эквивалентен `enum` из одного значения; указание `enum` и `const`
одновременно в одной схеме — InvalidSchema (а не пересечение множеств).
Каждое значение сериализуется компилятором в литеральную альтернативу:

- string → канонический JSON-литерал по таблице §2.2;
- boolean/null → `true` / `false` / `null`;
- числа → точная десятичная нормализация лексемы схемы **без binary64**:
  лексема парсится в десятичную дробь (мантисса + десятичная экспонента как
  рациональное число). Ограничение представимости: не более 400 значащих цифр
  и |записанная экспонента| <= 400; превышение — InvalidSchema.

Правила записи числового значения:

1. Ноль в любой записи — `0`: **`-0` → `0`**, `-0.0` → `0`, `-0e7` → `0`.
   Знак минус у нуля не сохраняется.
2. Если значение целое — десятичная целая запись без дробной части и
   экспоненты, по грамматике §4.1.
3. Нецелое значение, записанное без экспоненты, — запись `int.frac`: убрать
   ведущие нули целой части до одной цифры; убрать хвостовые нули дробной
   части.
4. Нецелое значение, записанное с экспонентой, — научная форма **сохраняется**:
   мантисса остаётся как в схеме с нормализацией нулей из п.3 (дробная часть,
   опустевшая после удаления хвостовых нулей, опускается вместе с точкой),
   экспонента нормализуется: `E` → `e`, без `+`, без ведущих нулей. Запись
   всегда соответствует грамматике §4.2.

Примеры:

| Лексема схемы | Значение | Каноническая запись |
|---|---|---|
| `1e2` | 100 | `100` |
| `1.50` | 3/2 | `1.5` |
| `0.1e1` | 1 | `1` |
| `-0` | 0 | `0` |
| `1.5e1` | 15 | `15` |
| `1E+2` | 100 | `100` |
| `12.340e0` | 12.34 | `12.34e0` |
| `1e-3` | 0.001 | `1e-3` |
| `1.5e-3` | 0.0015 | `1.5e-3` |
| `1.50E-3` | 0.0015 | `1.5e-3` |
| `10e-3` | 0.01 | `10e-3` |
| `-0.50` | -1/2 | `-0.5` |
| `10.0` | 10 | `10` |

Фильтрация и дубликаты:

- Каждое значение enum проверяется против `type` и `minLength`/`maxLength`;
  несовместимые значения отбрасываются. Если не осталось ни одного —
  UnsatisfiableConstraint.
- Сравнение чисел — точное по рациональному значению, без округления через
  binary64.
- Дубликаты значений после нормализации удаляются.
- enum без явного `type`: тип выводится из значений (все значения одного типа;
  смешанный enum — UnsupportedFeature в MVP).

## 7. Массивы

- `items` — одна схема для всех элементов (обязателен для `array`).
- `minItems`/`maxItems` — неотрицательные целые; `minItems > maxItems` —
  UnsatisfiableConstraint. Отсутствие `maxItems` — отсутствие семантического
  верхнего предела (внутренне UNBOUNDED).
- Автомат: open (`[`) → body: если `count >= max` — только `]`; `]` завершает
  при `count >= min`, иначе ошибка; после элемента — sep: `,` → следующий
  элемент (если `count >= max` — ошибка), `]` → завершение при `count >= min`.
- После запятой элемент обязателен: `]` сразу после запятой — ошибка.
  **Trailing comma запрещён всегда** (как и в объектах, §5).
- Повторения представлены счётчиком; большой `maxItems` не разворачивается в
  копии грамматики.

## 8. Завершение документа

- EOS разрешается только в принимающем состоянии: стек разбора пуст либо
  каскад «вершина — число в complete-состоянии» виртуально схлопывается до
  пустого стека без чтения байтов.
- При нескольких зарегистрированных EOS IDs правила одинаковы для всех.
- Повторный EOS после принятого EOS: состояние остаётся принимающим, accept
  успешен, документ не меняется (финализация — `finish`).
- Корректный префикс не выдаётся за готовый документ: `finish` требует
  принимающего состояния.

## 9. FR-3: буквальные альтернативы

- Вход: JSON-массив строк UTF-8 (уже декодированные значения, без
  JSON-экранирования). Список непустой.
- Дубликаты удаляются. Пустая строка допустима как вариант (литерал длины 0,
  завершается мгновенно).
- Допустимый ответ — ровно одна строка из списка целиком, raw-байты без
  кавычек и экранирования.
- Общие префиксы альтернатив, Unicode и токены, перекрывающие несколько
  символов, поддерживаются (каждая альтернатива — отдельная ветвь разбора).
- Формат не смешивается с произвольными regex.

## 10. Завершимость и отсутствие тупиков

**Утверждение.** После compile-time проверок (docs/DESIGN.md §1.7, фильтрация
enum §6, проверки min<=max, ацикличности $ref, лимита глубины) любое состояние
разбора, не являющееся ошибкой, продолжимо до валидного завершённого документа.

**Рассуждение по конструкциям** (индукция по стеку разбора):

1. *Строка.* Из любого корректного состояния строки (normal/escape/`\u00xx`,
   счётчик <= max) существует продолжение до закрытия: если `count < min`,
   добираются символы `'a'` (каждый — валидный, UTF-8 DFA в rem=0, min
   конечен); escape-состояния завершаются за <= 3 байта по таблице §2.2;
   незавершённый UTF-8 добирается continuation-байтами из текущего диапазона.
   После `count >= min` и `rem == 0` закрывающая `"` принимается. maxLength не
   мешает: состояние с `count > max` отвергнуто при инкременте и в живых
   состояниях отсутствует.
2. *Число.* В complete-состоянии число завершается «лениво» любым
   разделителем родителя (§4.3). В не-complete состоянии продолжение есть
   всегда: после `-` — цифра, после `.` — цифра, после `e`/`e+`/`e-` — цифра;
   цифра переводит в complete-состояние.
3. *Массив.* Если `count >= min`, допустимо `]`; если `count < min`, то
   `count < max` (иначе состояние было бы отвергнуто) и допустим следующий
   элемент; элемент — схема, к которой применима индукция. min/max конечны
   либо max = UNBOUNDED, поэтому `min` достижимо за конечное число элементов.
4. *Объект.* Правило кандидатов §5 гарантирует: в фазе key либо допустимо `}`
   (required не осталось), либо среди кандидатов есть ближайший required-ключ,
   и его выбор не блокируется. Пропустить required-ключ невозможно по
   построению. Значения свойств — схемы, к ним применима индукция. Число
   свойств конечно.
5. *enum/const.* После фильтрации §6 множество альтернатив непусто (иначе
   UnsatisfiableConstraint на этапе компиляции); каждая альтернатива —
   конечный литерал.
6. *choice.* Хотя бы одна ветвь жива — иначе состояние было бы ошибкой разбора
   (ветвь отбрасывается при первом непринятом байте). Живая ветвь продолжима
   по индукции.
7. *$ref.* Граф ссылок ацикличен (проверено при компиляции), поэтому раскрытие
   ссылок конечно и сводится к конечному дереву конструкций.

**Следствия.**

- Runtime-проверка допустимости токена сводится к: «все байты токена принимаются
  хотя бы одной ветвью разбора»; отдельной проверки достижимости завершения не
  требуется — она обеспечена конструкцией.
- Тупик возможен только в вырожденном случае: ни один токен словаря и ни один
  EOS не принимается текущим состоянием (например, словарь не покрывает
  обязательный следующий байт). Тогда движок возвращает DeadEnd с состоянием и
  причиной; автоматически разрешать весь словарь или EOS запрещено (ТЗ FR-4).
- Контракт §3.1 ТЗ («после принятия токена существует завершение») выполняется
  для всех токенов, пропущенных маской, без дополнительных проверок.

## 11. Отличия языка canonical-v1 от полного JSON / JSON Schema

canonical-v1 — явное сужение представлений. Следующие документы валидны по
RFC 8259 и/или исходной JSON Schema, но **не входят** в язык canonical-v1:

1. Экспоненциальная запись целого значения для `type: integer` (`1e2`, `1E+2`,
   `10e0`): допустима исходной JSON Schema как целое число, но язык integer
   canonical-v1 — только десятичная запись без экспоненты (`100`).
2. Дробная запись целого значения для `type: integer` (`100.0`, `100.00`):
   не входит в язык integer.
3. Пробелы вне строк: `{ "a": 1 }`, отступы, переводы строк — вне языка;
   сериализация всегда компактная.
4. Альтернативные escapes строк: `\/`, `\u0041`, `\u001B` (верхний регистр hex),
   `\u0009` вместо `\t`, `\uXXXX` для кодов >= 0x20 — запрещены; допустима
   ровно таблица §2.2.
5. Порядок ключей, отличный от порядка объявления в `properties`, — вне языка,
   даже если JSON Schema порядок не ограничивает.
6. Ключи, не объявленные в `properties` (`additionalProperties` в MVP всегда
   `false`), — вне языка.
7. Пропуск required-ключа — вне языка по построению (§5); полная JSON Schema
   допускает любой порядок и наличие/отсутствие необязательных ключей в любом
   порядке.
8. `NaN`, `Infinity`, `-Infinity`, шестнадцатеричные числа, ведущие нули,
   `+1`, `.5`, `1.` — не JSON-числа и вне языка.
9. Возможности JSON Schema вне профиля FR-1 (`anyOf`/`oneOf`/`allOf`/`not`,
   `minimum`/`maximum`/`multipleOf`, `pattern`/`format`, `uniqueItems`,
   boolean-схемы, внешние `$ref` и т.д.) не задают языка: такие схемы
   отклоняются компилятором с UnsupportedFeature до генерации, а не
   «ослабляются».

Полнота заявляется только относительно языка canonical-v1: движок не запрещает
ни одного документа этого языка для поддерживаемой схемы (ТЗ §3.2). Полнота
относительно всех сериализаций, допустимых исходной JSON Schema, не заявляется;
различия отражаются в отчёте компилятора и тестах.
