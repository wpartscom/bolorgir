# ADR-0015: standalone regular-expression constraint

- Status: **proposed** (2026-10-11).
- Context: the engine compiles an ECMA-262 subset to a DFA over Unicode
  scalar values for the JSON Schema `pattern` keyword
  (`src/pattern.zig`), but a caller that wants plain text matching a
  regular expression (a serving engine's `regex` request type) has no
  constraint format for it. The JSON parser's frames
  (`src/parser.zig`) model JSON lexemes: a string frame expects quotes
  and escapes, and a new frame kind would have to be handled by every
  exhaustive switch over frames in the parser, the certificates, the
  witness synthesis and the probe.

## Decision 1: a separate constraint kind with its own session state

`BLG_CONSTRAINT_REGEX` (kind 2) compiles `data`, the UTF-8 pattern, with
`pattern.compile(..., .{ .mode = .full })`: the whole text must match,
ECMA-262 `^(?:p)$`. The grammar carries the program (`Grammar.regex`)
and no JSON nodes. A session of such a grammar keeps a `regex.State`
(DFA state, pending bytes of one UTF-8 sequence, a flag for the first
byte) instead of parser states; `blg_fill_mask`, `blg_accept_token`,
`blg_can_end`, `blg_finish`, rollback and draft validation dispatch on
`Grammar.regex` in `src/c_api.zig`. The JSON frame machinery is not
touched.

Rejected: a raw-text string frame in the parser. It would reuse the mask
fast path and the certificates, but those assume JSON string content
(`"` ends, `\` escapes, no raw control characters) and every one of them
would need a raw-mode branch; the separate path is smaller and cannot
change JSON masks.

## Decision 2: exactness by live DFA states, byte-complete vocabularies only

At compile time a reverse search from the accept states marks the live
states: those from which an accept state is reachable. A full code point
is legal only when it leads to a live state; a lead or continuation byte
of a pending UTF-8 sequence is legal only when some code point the
pending bytes can still complete to leads to a live state (the code point
interval the bytes allow is intersected with the transitions of the
current state). Overlong forms, surrogates and values above U+10FFFF are
illegal bytes, as in the JSON string machine.

With every single byte available as a token, any live state can be
completed one byte at a time, so a byte-legal token never leads to a
dead end and the mask is exact without a completion search. This is the
language-level reachability of the T1 item 3 distinction; on a vocabulary
without all single bytes it does not imply token-level reachability, so
such a vocabulary is refused at compile time with
`BLG_ERR_UNSUPPORTED_TOKENIZER`. The `pattern` keyword needs the exact
length descriptors of `certStrPat` because a string frame also carries
`minLength`/`maxLength` bounds; a standalone regex has no length bound
beyond the pattern itself, and the live-state set is the exact answer
for it.

A pattern whose start state is not live matches nothing:
`BLG_ERR_UNSATISFIABLE_CONSTRAINT`.

**Deviation from the original requirement.** The task asked for
completion reachability through the DFA length descriptors
(`certStrPat`). This decision uses the live-state set instead, for the
reason above. It is a proposed change of that requirement, not an
approved one: until the owner accepts this ADR, that item stays open and
the implementation is a candidate for review.

## Decision 3: masks by walking the vocabulary trie

The mask walks the token prefix trie of the context (`tokenizer.Trie`)
from the session state: an edge is followed only while its byte is legal,
so tokens sharing a prefix share its feed and a dead prefix prunes its
subtree. EOS bits are set when the text matches as it stands; special
tokens are never set. The walk charges the work budget per visited node
and observes cancellation. The mask cache and the ADR-0007 fast path are
not used for this kind; precompute mode skips the warm-up.

## Decision 4: decoder and diagnostics

A strip-lead-space decoder (`BLG_TOKENIZER_STRIP_LEAD_SPACE`) is modeled
as for JSON grammars: the first generated byte, when it is a space, is
dropped and the DFA starts after it; otherwise the text starts with that
byte. Unsupported constructs (backreferences, lookaround, `\b`, `\B`,
`\p{...}`, inline flags, legacy octal) are `BLG_ERR_UNSUPPORTED_FEATURE`
with the byte offset of the construct's first byte (the `(` of a group
form, the `\` of an escape) in `schema_offset`
(`pattern.Options.error_offset`); size limits report the pattern length;
malformed syntax is `BLG_ERR_INVALID_SCHEMA` with the offset where
parsing stopped. `profile` must be NULL (`BLG_ERR_INVALID_ARGUMENT`) and
the probe flags are refused (`BLG_ERR_UNSUPPORTED_FEATURE`): the probe is
defined for JSON grammars.

## Decision 5: identity and caching

The artifact cache key and the grammar identity include the kind, so a
regex and a JSON schema with the same bytes never share an artifact. The
program depends on the strip-lead-space flag of the context, which is
fixed per context like the vocabulary.

## Verification

- Zig: `src/regex.zig` tests (full match, live states, ECMA classes,
  UTF-8 legality, strip-lead-space, refusals) and the ABI test in
  `src/c_api.zig` (masks, refusals, rollback and validation on a regex
  session, refusal of a partial vocabulary).
- Python: `tests/test_regex_constraint.py` compares with an ECMA-262
  engine in `u` mode (`regress`) on random patterns from the syntax both
  accept, checks that every mask agrees with the accept of each byte,
  runs random generation passes whose texts must match, and has table
  tests for constructs outside the intersection. The reference runs in
  a worker process with a memory and time limit
  (`tests/ecma_reference.py`): regress 2025.10.1 does not terminate on
  some loops with a nullable body (`(?:a?)+?b` on "ac", `((a?)+)+b` on
  "aac"); such a case has no expected result, is listed and may be at
  most 1% of the compared cases. The suite is green on both Python
  backends (package and ctypes) for the byte-level vocabulary.
- The syntax and semantics table of the supported ECMA subset lives in
  `docs/supported_features.md`; the serving integration compiles regex
  requests on the pinned model vocabulary (the Qwen2.5-0.5B-Instruct
  tokenizer converts to a byte table and all three request kinds compile
  and mask on it).
